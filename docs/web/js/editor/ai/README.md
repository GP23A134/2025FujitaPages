# AIチャット

編集画面は `main.js` を入口にし、AIチャットを9つの機能単位に分けています。分割・統合の調整値は `tuning-limits.js` に集約し、編集データの確定的な変更は既存の `web/js/editor/events.js` が担います。`edit.html` は `main.js` を読み込み、AIチャットの依存モジュールは `import` で解決します。

## モジュール

| ファイル | 担当 |
| --- | --- |
| `main.js` | 画面初期化、会話状態、送信フロー、モジュール間の連携 |
| `chat.js` | 会話履歴の保存・復元と履歴一覧・メッセージの描画 |
| `conversation-renderer.js` | 会話アイテム、確認事項、表示状態、スクロールの描画・同期 |
| `request-progress.js` | 送信準備・処理中の進捗表示、状態ラベル、経過時間タイマー |
| `request.js` | 依頼本文・対象範囲・分割計画、AI送信と全体範囲の再試行、分割回答の統合、選択に応じたプロンプト例 |
| `proposal-view.js` | 変更案一覧の描画とプレビュー操作の接続 |
| `ai-client.js` | クラスID変換、Responses API形式、HTTP通信と応答解析 |
| `proposal-engine.js` | 応答検証、依頼別の操作ポリシー、提案操作の検査 |
| `proposal-preview.js` | 変更案のプレビュー、操作選択、ナビゲーション、適用 |
| `tuning-limits.js` | 開発者設定と分割・統合処理で共有する数値範囲と初期値 |
| `web/js/editor/events.js` | 利用者が適用した提案を編集データへ反映 |

## 送信フローを `main.js` に残す理由

`main.js` の送信処理は、画面の確認、対象範囲、分割リクエスト、応答の統合、会話履歴の更新を順番に調整します。各機能モジュールをつなぐ役割があるため、現段階ではオーケストレーションとして `main.js` に置いています。進捗表示、会話表示、変更案一覧、通信、送信データの計画、応答検証などの個別処理は、それぞれのモジュールに分離しています。

この処理をさらに分割する場合は、送信全体の状態やキャンセル処理、分割結果の統合を一つのオーケストレーターに移し、画面表示と編集状態は引数やコールバックで渡す形にします。依存関係が明確になり、単独で確認できる境界ができた段階で行います。

## 回答モード

- AIチャットのヘッダーで「改善提案モード」と「評価モード」を切り替えます。初期状態は改善提案モードです。
- 改善提案モードでは全操作種別を許可します。操作の許可範囲は依頼文から推測せず、選択範囲や階層ルールなど既存の適用検証を維持します。
- 評価モードでは共通プロンプトに評価専用プロンプトを加えます。変更案と確認質問は生成させず、情報が足りない場合は判断できない点と理由を説明します。受信後の検証でも提案と質問を除外します。
- モードは確認質問への回答にも引き継ぎます。分割結果のキャッシュキーにはモード別のプロンプト・指示が含まれ、別モードの結果を再利用しません。
- 返答文は提案カードの操作一覧を繰り返さず、全体の傾向、判断理由、範囲ごとの違いを説明します。分割回答の統合にも同じ読みやすさの方針を適用します。

## プロンプト例

- `web/data/config/ai-prompt-examples.json`の例を「基本」「未分類」「対象クラス」「上位クラス」「中間クラス」「複数選択」「全体参照」に分けて表示します。
- 選択クラスの種類・件数・親の違い、未分類配下の選択、全体参照の設定に応じて、該当する例だけを表示します。
- 例の文面と表示条件は同JSONで管理し、選択条件の判定は`request.js`、グループ表示は`main.js`が担当します。

## 送信コストの抑制

- 分割評価の結果は、モデル・指示文・依頼文・データ版・対象範囲が一致した場合に再利用します。内容が変わった範囲だけ再送し、同一データの追加相談では保存済みの全体要約を使います。
- 全体参照の分析要約も保存します。同じデータ版・選択範囲での通常の追加相談は要約だけを送り、データ変更、範囲変更、構造の再確認、明示的な再分析依頼では全体スナップショットを送り直します。
- Responses APIにはモデルと固定システム指示から作った安定した`prompt_cache_key`を渡し、同じモデル・指示の入力でプロンプトキャッシュを利用しやすくします。キャッシュのヒットはAPIの使用量で確認します。
- 出力上限の初期値は通常5,000、分割チャンク3,000、分割結果の統合4,500、全階層横断提案4,000トークンです。`?dev=1`で表示される開発者設定から調整でき、各上限は選択中モデルの最大出力トークン数以下に制限されます。提案数は5〜1,000（初期30）、確認事項数は1〜100（3）、1提案あたりの操作数は5〜1,000（40）、不確実点数は1〜100（5）、分割回答のカテゴリ別所見数は1〜80（3）、統合結果のカテゴリ別所見数は1〜120（8）に調整できます。同欄では送信入力上限（初期値48,000文字、12,000〜128,000文字）、分割送信の有効/無効、1回の分割単位数（1〜6）、最適化の分割開始件数（1〜30）、統合回数（1〜12）も調整できます。分割送信を無効にした場合、設定した送信上限を超える依頼は送信できません。
- 回答は必要な結論と根拠に絞ります。詳しい説明を求められた場合や、変更案の安全な操作を示す場合に必要な情報は省きません。
- 応答JSONでは`m/p/q/d`や`i/t/s/r/o`などの短縮キーと、短い操作種別コードを使います。受信後にブラウザー内で従来の`message`、`proposals`、`operations`形式へ展開するため、画面表示・提案検証の内部形式は変わりません。
- 通常回答の共通ルールは`web/data/config/ai-system-prompt.md`にまとめます。提案モードでは自由度に応じて`web/data/config/ai-proposal-freedom-1.md`から`ai-proposal-freedom-5.md`のいずれか1つを読み込み、共通ルールの後ろに連結して送信します。共通プロンプトは依頼内容と操作上の必須ルールを定め、段階別プロンプトは提案の幅と曖昧さの扱いを定めます。送信ごとの範囲・分割・提案方針はさらに追加指示として渡します。統合処理では`web/data/config/ai-synthesis-prompt.md`を専用指示として使います。APIに送る前に指示をデータJSONから分離し、返答形式はAPIスキーマの短縮キーに合わせます。
- 全階層をまたぐ移動先の検索方式は、提案自由度にかかわらず「全階層を比較」または「階層横断の候補検索」のユーザー設定に従います。候補検索方式では候補を絞り、網羅比較ではないことを回答に反映します。自由度は候補の広さ・案の出し方を定めます。

## 送信と処理中の表示

- 実行ボタンを押した時点から経過時間を計り、準備中は「依頼内容を準備しています」と秒数をチャット欄に表示します。送信後も作業段階と秒数を表示します。
- 表示する主な段階は、送信内容の確認待ち、AIに送信中、結果を処理中、分割処理中、結果を統合中、変更を適用中です。分割処理は完了数／全体数を表示します。
- 分割結果の統合には、短い回答要約、上位クラス範囲・入力済み件数、カテゴリ別の構造化所見を使います。操作例や全クラス一覧は渡さず、カテゴリ所見の代表例数と文章量を入力上限に応じて圧縮します。重複候補・分類の偏り・分類漏れ/孤立・その他をそれぞれ判定し、所見あり・確認されず・判断不能を区別します。
- カテゴリと各所見は比較対象範囲と実際に判定できた範囲を別々に持ちます。重複・偏りは比較対象となる全対象範囲を必須にし、分類漏れ・その他は完了済みの局所範囲で判定します。未完了範囲がそのカテゴリの必須範囲でない場合は保留にせず、必要範囲が不足する所見は除外し、範囲内で根拠が揃った所見は残します。
- APIへ送る各リクエストの指示文とデータを合算した送信文字数上限を送信直前に適用します。初期値は48,000文字で、開発者設定から12,000〜128,000文字の範囲で調整できます。過去の応答IDが参照する会話履歴はこの文字数には含めず、モデル側のコンテキスト上限として別途考慮します。出力トークン数や分割・統合の処理上限も開発者設定で調整できます。出力トークン数はモデルの最大値を超えず、送信時にもモデル上限で再制限します。
- 分割送信では全上位・中間クラスのID・種別・名称・親IDを一度共有し、その応答IDを各分割の共通の前提として使います。計画時はプロンプト分を差し引き、階層情報と分割入力を収めます。
- 改善提案モードで全階層が揃い、全チャンクが完了した場合は、選択中の全対象クラスと全階層を入力する横断操作検討を実行します。最終応答の評価対象ID一覧もアプリ側で照合します。必要範囲が揃わない、評価対象が不足する、または入力上限を超える場合は横断評価の未完了として扱います。
- 横断操作は既存の変更元・移動先・削除安全性検証に通し、元データを直接変更しません。個別案と操作列が完全一致すれば根拠を統合します。同じクラスへの操作が競合すれば代替案として表示し、同じ代替グループからは一案だけ適用できます。
- 統合成否・カテゴリ別の比較可否・全範囲横断操作の完了状態を別々に保持して表示します。

## 監査記録と料金表示

- AIを利用すると、依頼文と選択範囲または全体分析時のクラス情報をOpenAI APIへ送信します。APIキーはページを閉じるまでメモリー上で使い、ブラウザー保存領域には記録しません。
- 会話履歴は利用者が「保存」を選んだ場合だけこのブラウザーの`localStorage`へ保存します。共有端末では保存済み相談を解除するか、相談内容を保存しないでください。

- AI提案を適用したとき、提案全体と実際に選択・適用した操作、適用日時、任意の記録者名、変更前後のクラス階層を記録します。
- 記録は現在のブラウザーの`localStorage`に最大100件保存し、編集画面の設定から確認できます。`class-update.json`には含めず、ブラウザーの保存領域を消去すると記録も失われます。記録者名は任意入力で、本人確認には使われません。
- 料金設定は`web/data/config/ai-models.json`で管理します。価格確認日と出典を記録し、単価を確認できたモデルだけ料金概算を表示します。概算は標準・短コンテキスト単価を使い、実際の請求額とは一致しない場合があります。

## 提案プレビュー

- 選択済みの中間クラスは参照可能な上位・中間クラスへ移動できます。選択済みの上位クラスは未分類を除き、中間クラスに変換して参照可能な上位・中間クラスの下へ移動できます。移動先が自分自身や配下になる操作は拒否します。
- 選択済みの中間クラスは独立した上位クラスへ昇格できます。配下の中間・対象クラスは種類と親子関係を維持し、昇格対象と同名の上位クラスがある場合は拒否します。
- 上位・中間クラスの削除は提案自由度に従います。段階2〜5では配下全体が編集範囲にあり、必要な子の移動を含む場合だけ削除できます。段階1では分類上の存在価値がないクラスの削除を未選択の配下があっても提案でき、適用時は配下を削除せず、上位クラス配下の中間クラスを上位化し、対象クラスを有効な親へ移動します。変更はプレビューに反映します。
- 許可されない操作は理由を付けて除外し、残りの操作を適用時と同じ検証で確認します。残りだけでは成立しない提案は操作全体を止め、理由を示します。AIへの自動修正依頼は行いません。
- 依頼意図・分割タスクごとの許可操作は`proposal-engine.js`で一元的に決め、応答検証と編集データへの適用で同じポリシーを使います。応答の操作形式、ID、変更可能範囲、移動先、同じ親への移動などを検査し、安全でない操作を除外します。同名クラスが複数あるときは親階層から再利用先を一意に決め、決められない操作を除外します。親IDまたは表示上の親経路が変わらない移動は除外し、変更一覧には変更前後の親経路を表示します。
- 分割タスクの許可操作説明は同じ操作ポリシーから生成し、プロンプトと応答検証の許可範囲を揃えます。
- 変更前後のツリーでは操作種別ごとに色枠を表示し、移動タグは「移動」に統一します。追加の矢印は両ツリーの間に置く「＋ 追加」マーカーから新しいクラスへ引きます。
- プレビューでは変更前・変更後それぞれの親子関係を保ち、変更対象とその側の親経路だけを表示します。対応する変更対象の表示位置を反対側に合わせ、移動線の交差を抑えます。移動矢印はクラスごとに個別の線で表示し、移動先の親クラスごとにレーンと最初の折り曲げ位置を揃えます。親クラスごとのレーンは、移動元の要素が上にある順に変更後側から配置します。先端は変更後の対象クラスに置きます。この並び替えはプレビューだけに適用します。
- 変更一覧は初期状態で閉じています。移動項目にカーソルを合わせるかキーボードでフォーカスすると、移動対象と変更前・変更後それぞれの直接の親クラスを拡大表示し、移動矢印を強調表示します。ツリー上で対象クラス、上位・中間クラス、追加クラスにカーソルを合わせた場合も、対応する操作を拡大表示と配線の強調で示します。対象クラスと直接の親クラスを結ぶ横線と共有する縦線は色を変えずに太くします。ツリーのクラス間隔は少し広げます。
- 提案を選択してプレビューした後、利用者が適用した場合だけ編集状態を更新します。インスタンスと対象クラスの関係は変更しません。
